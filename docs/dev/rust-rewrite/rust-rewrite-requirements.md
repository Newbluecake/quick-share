# 需求文档: Quick Share Rust 全量重写

## 1. 概述

### 1.1 一句话描述

使用 Rust 全量重写 Quick Share，将其升级为一个面向 Linux、macOS 和 Windows 的无运行时依赖 CLI 文件传输工具：优先自动发现局域网接收端并加密直传，未发现接收端时自动回退到传统 Web 分享模式。

### 1.2 核心价值

- **单文件分发**：用户无需安装 Python、pip 或其他语言运行时。
- **更高性能**：提升启动速度、大文件传输吞吐和并发处理能力。
- **更低使用成本**：发送方只需执行 `sc <内容>`，程序自动选择设备直传或 Web 分享模式。
- **安全的局域网直传**：不依赖云端中转，使用设备身份、信任关系、加密传输和完整性校验。
- **跨平台一致性**：Linux、macOS 和 Windows 提供一致的核心命令与行为。

### 1.3 目标用户

- 需要在同一局域网的电脑之间快速传输文件、目录或文本的开发者和技术用户。
- 需要从服务器或无桌面环境临时分享文件的命令行用户。
- 不希望安装 Python 环境或复杂依赖的普通用户。
- 需要通过浏览器、二维码、`curl` 或 `wget` 接收内容的用户。

### 1.4 产品定位

Quick Share 是纯 CLI 工具，不提供桌面 GUI。它借鉴 LocalSend 的局域网设备发现、接收确认和可信设备模型，但以终端交互为主要入口，并保留原项目的临时 Web 分享能力。

Rust 版本允许破坏旧版命令和内部实现兼容性，以新的使用体验和长期可维护性为优先。

## 2. 需求与用户故事

### 2.1 命令模型

#### R-001：提供主命令和快捷命令

**用户故事**：作为命令行用户，我希望既能使用语义明确的完整命令，也能使用极短的发送和接收命令，以便兼顾可发现性与日常效率。

主命令至少包括：

```bash
quick-share send <路径...>
quick-share receive
quick-share serve <路径...>
quick-share devices list
quick-share devices rename <设备>
quick-share devices remove <设备>
quick-share config
quick-share update
```

快捷命令：

```bash
sc <内容>   # 自动发送模式
rc          # 接收模式
```

**验收标准**：

- `sc` 的核心行为等价于 `quick-share send`。
- `rc` 的核心行为等价于 `quick-share receive`。
- 安装程序创建快捷命令前检查名称冲突。
- 不得静默覆盖系统中已有的 `sc` 或 `rc` 程序。
- 快捷命令冲突不会影响 `quick-share` 主命令使用。

### 2.2 自动发现与模式选择

#### R-002：自动发现局域网接收端

**用户故事**：作为发送方，我希望工具自动发现同一局域网中正在运行的接收端，从而无需手工输入 IP 地址和端口。

**验收标准**：

- `rc` 启动后能够广播可发现的设备信息。
- `sc <内容>` 自动扫描当前局域网内兼容的 Quick Share 接收端。
- 正常局域网环境下，设备发现通常在 2 秒内完成。
- 扫描结果排除发送设备自身、重复设备和不兼容服务。
- 发现一个或多个设备时，发送方可以明确选择目标设备。
- 未发现设备时，程序自动进入传统 Web 分享模式。

#### R-003：允许用户强制选择模式

**用户故事**：作为关注可预测性和安全性的用户，我希望能够绕过自动判断并明确指定设备直传或 Web 分享模式。

命令示例：

```bash
sc --peer <设备> <路径...>
sc --web <路径...>
```

**验收标准**：

- `--peer` 跳过自动回退，只尝试向指定设备发送。
- 强制设备直传失败时返回非零退出码和明确错误，不自动公开 Web 链接。
- `--web` 跳过设备扫描并直接启动传统 Web 分享。
- 已发现设备在拒绝、确认超时或传输失败后，不自动切换为 Web 模式。
- 自动回退仅发生在扫描结束且没有发现任何可用接收端时。

### 2.3 接收、身份与信任

#### R-004：提供纯终端接收模式

**用户故事**：作为接收方，我希望只运行一个终端命令即可等待和接收附近设备发送的内容。

**验收标准**：

- `rc` 在前台启动接收服务并持续显示可理解的状态。
- 收到陌生设备请求时，显示设备名称、网络地址、内容类型、文件清单、数量、总大小及设备指纹或短验证码。
- 接收端提供“接受一次”“接受并信任”“拒绝”三种操作。
- 拒绝和确认超时不会创建不完整的最终文件。
- Ctrl+C 能够安全停止接收服务及正在等待的新请求。

#### R-005：基于设备身份维护信任关系

**用户故事**：作为经常在固定设备之间传输内容的用户，我希望信任已验证设备，以减少重复确认，同时不能因 IP 地址变化而失去身份识别能力。

**验收标准**：

- 每台设备具有持久化的身份密钥或等价安全身份。
- 信任关系绑定设备身份，不只绑定 IP 地址。
- “接受并信任”后，可信设备默认可以自动发送。
- 用户可通过配置将可信设备改为每次仍需确认。
- 提供可信设备的查看、重命名和移除能力。
- 设备身份变化或密钥不匹配时按陌生设备处理，并显示安全提示。

#### R-006：保护传输机密性和完整性

**用户故事**：作为用户，我希望局域网中的其他设备不能轻易窃听或篡改传输内容。

**验收标准**：

- 设备直传必须经过加密和身份校验。
- 每次传输必须校验内容完整性。
- 身份密钥、信任记录和敏感配置必须存放于平台标准配置目录，并限制文件访问权限。
- 日志不得输出私钥、完整认证凭据或其他敏感信息。
- 不允许在设备直传失败后静默降级到明文传输。

### 2.4 文件、目录、文本与剪贴板

#### R-007：支持文件与目录传输

**用户故事**：作为发送方，我希望一次发送一个或多个文件和目录，并在接收端保留正确结构。

**验收标准**：

- 支持单文件、多文件、空文件和目录。
- 目录传输保留相对目录结构和空目录。
- 支持大于 4 GB 的单文件。
- 文件读写采用流式处理，内存使用不随文件大小线性增长。
- 发送前显示内容数量和总大小；无法读取的路径在传输前明确报告。
- 接收端处理同名文件、已存在目录、权限不足和磁盘空间不足时，不得静默覆盖或丢弃数据。

#### R-008：支持符号链接并采用安全默认值

**用户故事**：作为安全敏感用户，我希望传输符号链接时不会在不知情的情况下读取链接目标。

**验收标准**：

- 默认传输符号链接本身，不自动跟随链接目标。
- 只有显式使用 `--follow-links` 时才读取并发送链接目标内容。
- 跟随链接前显示真实目标或提供等价的可审计信息。
- 损坏链接、循环链接、越界目标和权限错误必须明确报告。
- Windows 权限或跨平台链接语义不兼容时，给出明确错误或有记录的安全降级，不得静默改变含义。

#### R-009：支持文本与剪贴板内容

**用户故事**：作为用户，我希望在设备之间快速发送短文本或当前剪贴板内容，而不必先创建临时文件。

命令示例：

```bash
sc --text "hello"
sc --clipboard
```

**验收标准**：

- `--text` 发送用户提供的文本内容。
- `--clipboard` 读取发送端系统剪贴板并发送。
- 接收端显示文本来源和安全摘要，并尝试写入系统剪贴板。
- 无桌面会话或系统剪贴板不可用时，将文本输出到终端。
- 接收方可通过 `--output` 将文本保存到文件。
- 程序不得自动执行、打开、解释或渲染收到的文本为可执行内容。
- 剪贴板不可用时给出可操作的错误或降级提示。

### 2.5 传统 Web 分享模式

#### R-010：无设备时自动回退到传统模式

**用户故事**：作为发送方，即使接收设备没有安装 Quick Share，我也希望通过浏览器、二维码或常见下载工具完成分享。

**验收标准**：

- `sc <内容>` 未发现任何接收端后自动启动 Web 分享服务。
- 程序明确提示已进入传统模式，避免用户误解传输方式。
- 输出浏览器链接、二维码及可复制的 `curl`/`wget` 命令。
- 用户可使用 `quick-share serve <路径...>` 或 `sc --web <路径...>` 直接进入该模式。

#### R-011：保留并重写传统分享能力

**用户故事**：作为旧版用户，我希望仍可通过浏览器分享和接收内容，同时获得更清晰、快速的界面和单文件安装体验。

传统模式至少支持：

- 单文件、多文件和目录分享；
- 浏览器文件列表和目录浏览；
- 文件下载和目录下载；
- 二维码；
- 浏览器上传页面和接收目录配置；
- 下载次数限制；
- 服务超时自动关闭；
- 实时传输进度与日志；
- 只暴露用户明确选择的文件和目录。

**验收标准**：

- 未选择的文件系统路径不能通过路径遍历、符号链接逃逸或构造 URL 访问。
- 上传内容必须经过文件名、目标路径、大小和冲突策略校验。
- 下载次数限制和服务超时达到后，服务能够安全关闭。
- Web UI 在现代桌面和移动浏览器中可用，但不要求开发原生移动客户端。
- Web UI 和静态资源随单一二进制分发，不依赖外部运行时。

#### R-012：传统模式不得静默扩大网络暴露

**用户故事**：作为安全敏感用户，我希望清楚知道 Web 分享的监听范围、加密状态和有效期。

**验收标准**：

- 启动时显示监听地址、可访问网卡、分享内容、有效期和次数限制。
- 默认不静默暴露到公网接口。
- 默认不允许静默降级到明文公网传输。
- 局域网浏览器加密、临时证书和显式 `--allow-http` 的最终策略在设计阶段确定。
- 如果使用明文 HTTP，必须由用户显式允许并显示醒目风险提示。
- Web 链接应包含足够随机、不可预测的访问凭据或采用等价访问控制。

### 2.6 性能、可靠性与恢复

#### R-013：提供高性能流式传输

**用户故事**：作为传输大文件的用户，我希望 Rust 版本充分利用局域网和磁盘性能，同时保持稳定的资源占用。

**验收标准**：

- 大文件使用有界缓冲流式读写。

- 多文件支持并行或流水线处理。
- 默认一次接收一个发送任务；后续并发策略可配置。
- 终端显示实时进度、已传输大小、总大小、速度和预计剩余时间。

#### R-014：支持断点续传和失败重试

**用户故事**：作为网络不稳定环境中的用户，我希望传输中断后可以继续，而不是重新发送全部内容。

**验收标准**：

- 支持大文件和多文件任务的断点续传。
- 恢复前验证目标文件、偏移量、内容身份和发送设备身份。
- 网络短暂中断支持有限次数的自动重试。
- 用户取消、对方拒绝、身份变化或完整性失败不得无限自动重试。
- 不完整数据必须使用临时状态保存，完成校验后再原子性提交为最终文件。
- 重启程序后是否恢复、恢复记录生命周期及清理策略在设计阶段明确。

#### R-015：提供明确的异常处理

**用户故事**：作为用户，我希望失败时知道原因、当前数据状态以及下一步该怎么做。

必须覆盖的异常包括：

- Windows Public 网络 profile 或入站防火墙阻止 receive/Web 监听；
- 接收方拒绝或确认超时；
- 网络切换和连接中断；
- 磁盘空间不足；
- 路径不可读或不可写；
- 文件在传输过程中发生变化；
- 目标名称冲突；
- 完整性校验失败；
- 身份或证书不匹配；
- 端口占用；
- 剪贴板不可用；
- Windows、macOS、Linux 文件系统语义差异。

**验收标准**：

- 可恢复错误与不可恢复错误具有不同的退出状态和提示。
- CLI 错误包含可操作建议，不只输出内部异常。
- 失败后不留下伪装成完整文件的目标文件。
- 日志足以排查问题，但不会泄露敏感数据。
- 程序不得静默关闭或放宽系统防火墙；如需添加 Windows 规则，必须获得用户明确同意并限制到必要程序和网络 profile。

- [ ] 配置遵循“CLI > 环境变量 > TOML > 默认值”的优先级。
- [ ] 默认接收目录为系统 Downloads，且可覆盖。
- [ ] GitHub Releases 提供三平台预编译产物和校验值。
- [ ] Shell 与 PowerShell 安装脚本不会覆盖已有同名命令。
- [ ] `quick-share update` 验证更新包并支持失败回滚。

## 4. 技术约束

### 4.1 语言与运行时

- 核心程序必须使用 Rust 实现。
- 发布产物不得依赖 Python、pip 或语言运行时。
- Web UI 静态资源应嵌入发布产物或以等价方式随单文件可靠分发。
- 核心功能不得依赖桌面 GUI 框架。

### 4.2 平台

首版必须支持：

- Linux；
- macOS；
- Windows。

三平台必须具有一致的核心命令和协议行为。平台差异应封装在路径、权限、剪贴板、信号、文件替换、符号链接、防火墙和安装逻辑中，并提供平台专项测试。

### 4.3 网络与协议

- 设备发现仅面向本地网络，不依赖互联网或中心化服务。
- 发现协议应处理多网卡、自发现排除、重复结果、防火墙限制和网络切换。
- 直传协议必须支持版本协商、能力协商、设备身份、传输授权、进度、取消、恢复和完整性校验。
- 协议字段、兼容策略、端口选择和发现机制在设计阶段固化并形成文档。
- 任何自定义加密协议均不可自行发明底层密码原语，应使用成熟协议和经过审查的 Rust 库。

### 4.4 性能与资源

- 文件数据必须采用有界缓冲流式处理。
- 禁止将大文件完整载入内存。
- 并发必须具有上限和背压，避免耗尽文件描述符、内存或网络资源。
- 性能验收必须使用可复现的基准环境、文件规模和测量方法。
- 断点续传状态必须可验证、可清理，并防止错误拼接不同内容。

### 4.5 安全

- 设计阶段必须产出威胁模型，至少覆盖局域网窃听、冒充设备、中间人、重放、路径遍历、符号链接逃逸、恶意文件名、资源耗尽和恶意更新。
- 所有外部输入均视为不可信，包括发现广播、设备名称、文件元数据、路径、HTTP 请求、配置文件和更新响应。
- 接收文件必须先写入临时位置，校验完成后再提交。
- 默认配置应遵循最小暴露原则。
- 传统浏览器模式的 TLS、临时证书、访问令牌和显式明文开关必须在设计阶段给出可实施方案。

### 4.6 兼容与迁移

- 不要求保持 Python 版本的内部 API 或全部 CLI 参数兼容。
- 应保留用户价值明确的传统分享、上传、次数限制、超时和更新能力。
- 旧配置是否迁移、如何迁移以及无法迁移时的提示由设计阶段确定。
- Rust 版本发布前必须明确旧版弃用、版本号和回滚方案。

### 4.7 测试与质量

- 采用测试驱动开发覆盖协议、文件系统、安全边界和 CLI 行为。
- 单元测试不得替代真实的跨进程、跨网络和跨平台集成测试。
- 至少覆盖设备发现、陌生设备确认、可信设备、传输恢复、完整性失败、Web 路径隔离和自更新失败回滚。
- CI 必须构建并测试 Linux、macOS、Windows 目标。
- 关键安全路径应包含模糊测试、属性测试或等价的自动化异常输入验证。

## 5. 排除项

首版明确不包含：

- 桌面 GUI；
- Android 或 iOS 原生客户端；
- 云端存储或云端中转；
- 跨互联网自动发现；
- NAT 穿透或公网 P2P；
- 用户账户、中心化登录或在线设备目录；
- 后台常驻系统托盘应用；
- 自动执行、打开或解释接收到的文件和文本；
- 静默覆盖已有 `sc`、`rc` 或其他系统命令；
- 在设备直传失败后静默改用 Web 分享；
- 为兼容旧版而保留 Python 运行时；
- 未经用户明确允许的明文公网分享。

以下内容不是首版硬性要求，可在后续迭代评估：

- Homebrew、WinGet、Scoop、AUR 等包管理器发布；
- 浏览器扩展；
- 系统右键菜单、拖放或原生分享入口；
- 后台系统服务和开机自启；
- 跨平台移动端应用；
- 云端中继和跨网络传输。

## 6. 下一步

本需求复杂度为 **complex**，不应直接进入无设计编码。推荐使用规范驱动开发流程：

1. 运行 `dev-spec-dev`，并跳过重复需求澄清；
2. 盘点现有 Python 功能、测试和用户行为，形成迁移矩阵；
3. 设计 Rust workspace、模块边界和错误模型；
4. 对局域网发现协议、传输协议、TLS/身份模型和 Web 安全方案进行技术调研；
5. 编写威胁模型和跨平台兼容策略；
6. 定义协议版本、数据模型、断点续传状态和配置结构；
7. 制定分阶段 TDD 任务计划，建议至少拆分为：
   - Rust CLI 与配置基础；
   - 文件元数据、流式 I/O 与安全路径处理；
   - 接收服务与设备发现；
   - 身份、配对和信任管理；
   - 加密直传、进度、取消和完整性校验；
   - 断点续传与失败恢复；
   - 自动模式与传统 Web 回退；
   - Web UI、上传和访问控制；
   - 剪贴板与平台适配；
   - 安装、自更新、签名和三平台发布；
8. 在实施前使用 `review-plan --spec` 审查设计和任务计划；
9. 每个阶段通过单元测试、集成测试、安全测试和跨平台 CI 闸门后再进入下一阶段。

建议下一条命令：

```text
/devagent:dev-spec-dev rust-rewrite --skip-requirements
```
