# 需求文档: Windows 远程文件与文件夹选择

## 1. 概述

### 1.1 一句话描述

为 Quick Share 增加双向对称的远程选择流程：远端发起传输操作后，由实际发送端选择要发送的文件或文件夹，由实际接收端确认或更改保存目录；第一阶段提供 Windows 原生图形交互。

### 1.2 核心价值

- Linux 用户发起操作后，可以直接在 Windows 上完成源文件或目标目录选择，无需手工输入 Windows 路径。
- 发送和接收遵循同一套对称规则，降低用户理解成本。
- 复用 Quick Share 现有设备身份、配对和传输能力，避免绕过已有安全边界。
- Windows 应用在交互式桌面会话中处于后台或托盘状态时，也能响应可信设备的请求。

### 1.3 目标用户与首期场景

目标用户是在 Linux 与 Windows 设备之间传输文件的 Quick Share 用户。

第一阶段重点支持以下两个场景：

1. **Linux 发起“接收”**：Windows 是实际发送端，Windows 用户选择一个或多个文件，或者选择一个文件夹，然后发送给 Linux。
2. **Linux 发起“发送”**：Windows 是实际接收端，Windows 用户确认该 Linux 设备上次使用的保存目录，或更改保存目录，然后接收内容。

Linux 端继续使用现有交互方式提供本地源路径或目标路径；Linux 原生图形选择器不属于第一阶段。

## 2. 需求与用户故事

### 2.1 双向对称交互模型

**用户故事：** 作为跨设备传输用户，我希望无论在哪一端发起操作，都由实际发送端选择内容、实际接收端选择保存位置，从而获得一致且可预测的行为。

#### 验收标准

- **WHEN** Linux 发起“接收”请求，且 Windows 是发送端，**THEN** Windows **SHALL** 进入发送内容选择流程。
- **WHEN** Linux 发起“发送”请求，且 Windows 是接收端，**THEN** Windows **SHALL** 进入保存目录确认流程。
- **WHEN** 请求被接受且本地选择完成，**THEN** 系统 **SHALL** 通过现有 Quick Share 安全传输链路开始传输。
- **WHEN** Windows 返回接受、拒绝、取消、忙碌或失败结果，**THEN** Linux 发起端 **SHALL** 显示对应的明确状态，而不是无限等待。
- **WHEN** 同一请求被重试或重复送达，**THEN** Windows **SHALL NOT** 为同一个请求重复打开多个窗口或重复启动传输。

### 2.2 Windows 发送内容选择

**用户故事：** 作为 Windows 用户，我希望先选择发送文件还是发送文件夹，再使用原生选择器选择内容。

#### 验收标准

- **WHEN** Windows 接受“请选择内容并发送”的请求，**THEN** 系统 **SHALL** 先显示一个小窗口，至少提供“选择文件”“选择文件夹”和“取消”。
- **WHEN** 用户点击“选择文件”，**THEN** 系统 **SHALL** 打开 Windows 原生文件选择器并支持多选。
- **WHEN** 用户点击“选择文件夹”，**THEN** 系统 **SHALL** 打开 Windows 原生文件夹选择器。
- **WHEN** 用户选择一个文件夹，**THEN** 系统 **SHALL** 递归发送文件夹内容并保留相对目录结构。
- **WHEN** 用户完成选择，**THEN** Windows **SHALL** 在传输开始前把可验证的文件清单和必要元数据交给现有传输流程。
- **IF** 选择结果为空、路径已失效或内容不可读，**THEN** 系统 **SHALL** 阻止传输、显示明确错误并通知发起端。
- **IF** 用户关闭小窗口或原生选择器，**THEN** 系统 **SHALL** 将本次请求标记为已取消，不启动传输。

### 2.3 Windows 接收目录确认

**用户故事：** 作为 Windows 接收方，我希望默认使用该发送设备上次使用的目录，同时可以在接收前更改目录。

#### 验收标准

- **WHEN** Windows 收到来自设备 A 的发送请求，**THEN** 系统 **SHALL** 显示保存目录确认窗口，并优先展示设备 A 上次成功确认的保存目录。
- **WHEN** 用户点击“更改目录”，**THEN** 系统 **SHALL** 打开 Windows 原生文件夹选择器。
- **WHEN** 用户确认当前目录，**THEN** 系统 **SHALL** 验证目录存在、可写且满足现有接收安全策略，然后才允许传输开始。
- **IF** 设备没有历史目录，**THEN** 系统 **SHALL** 默认展示 Windows 系统下载目录；若无法解析该目录，则要求用户选择目录。
- **IF** 历史目录已删除、不可访问或不可写，**THEN** 系统 **SHALL** 提示用户重新选择，不得静默回退到其他目录并开始接收。
- **IF** 用户关闭确认窗口或目录选择器且未确认有效目录，**THEN** 系统 **SHALL** 取消请求并通知发送端。

### 2.4 按设备持久化保存目录

**用户故事：** 作为拥有多台配对设备的用户，我希望 Windows 为每台设备分别记忆保存目录，并在应用重启后继续生效。

#### 验收标准

- **WHEN** 用户为已识别设备确认有效保存目录，**THEN** 系统 **SHALL** 以稳定的设备 ID 为键持久化该目录。
- **WHEN** 应用重启后再次收到同一设备的请求，**THEN** 系统 **SHALL** 恢复该设备上次确认的目录。
- **WHEN** 不同设备分别选择不同目录，**THEN** 系统 **SHALL** 保持这些记录相互隔离。
- **WHEN** 设备名称发生变化但受信任身份未变化，**THEN** 目录记录 **SHALL** 仍与该设备关联。
- **WHEN** 设备身份密钥变化或无法通过现有身份校验，**THEN** 系统 **SHALL NOT** 仅凭设备名称复用原目录记录。
- **IF** 用户取消目录选择，**THEN** 系统 **SHALL NOT** 用取消或无效路径覆盖上次有效记录。
- 持久化数据 **SHALL NOT** 包含设备密钥、传输令牌或其他不必要的敏感凭据。

### 2.5 配对、授权与防骚扰

**用户故事：** 作为接收远程请求的用户，我希望已配对设备可以快速操作，同时未配对或身份异常的设备不能未经确认弹出系统选择器。

#### 验收标准

- **WHEN** 请求来自当前仍受信任的已配对设备，**THEN** Windows **SHALL** 直接打开与请求类型对应的本地交互窗口。
- **WHEN** 请求来自未配对设备，**THEN** Windows **SHALL** 先显示包含设备身份信息、请求方向和操作类型的授权提示；只有用户明确接受后才能打开选择器或目录确认窗口。
- **WHEN** 未配对设备的单次请求被接受，**THEN** 该确认默认只授权当前请求，**SHALL NOT** 绕过现有正式配对流程自动建立永久信任。
- **WHEN** 已配对设备的身份密钥与保存记录不一致、信任已撤销或身份验证失败，**THEN** 系统 **SHALL** 按未受信任或拒绝路径处理，不得直接弹出原生选择器。
- **IF** 用户拒绝授权，**THEN** 系统 **SHALL** 通知发起端请求已拒绝且不打开选择器。
- **IF** 未受信任来源在短时间内重复发起请求，**THEN** 系统 **SHALL** 限流、合并或抑制重复提示，避免弹窗骚扰。
- 设备信任判断 **SHALL** 使用 Quick Share 现有经过验证的设备身份，不得仅依赖 IP 地址、主机名或用户可伪造的显示名称。

### 2.6 同名文件与目录冲突

**用户故事：** 作为 Windows 接收方，我希望目标目录出现同名内容时可以选择覆盖、跳过或重命名，并将选择应用到后续冲突。

#### 验收标准

- **WHEN** 接收清单与目标目录发生同名冲突，**THEN** Windows **SHALL** 在写入冲突项前显示冲突窗口。
- 冲突窗口 **SHALL** 提供“覆盖”“跳过”“重命名”和“取消传输”。
- 冲突窗口 **SHALL** 提供“应用到全部冲突”选项。
- **WHEN** 用户选择“重命名”，**THEN** 系统 **SHALL** 生成或接受一个在目标目录中不冲突的名称，并保留正确扩展名和目录结构。
- **WHEN** 用户选择“跳过”，**THEN** 系统 **SHALL** 不修改已有目标内容，并在最终结果中报告跳过项。
- **WHEN** 用户选择“覆盖”，**THEN** 系统 **SHALL** 仅覆盖本次明确授权范围内的冲突项，不影响其他文件。
- **WHEN** 用户选择“应用到全部冲突”，**THEN** 同一传输中后续同类冲突 **SHALL** 使用该策略，不再逐项弹窗。
- **IF** 用户取消冲突处理，**THEN** 系统 **SHALL** 停止本次传输，并通过现有清理机制避免将未完成临时文件暴露为完整文件。
- 对文件与目录、大小写不敏感名称以及 Windows 保留名称的处理 **SHALL** 符合现有路径安全策略和 Windows 文件系统规则。

### 2.7 后台唤起与窗口生命周期

**用户故事：** 作为 Windows 用户，我希望 Quick Share 在后台或托盘运行时仍能让我看到可信的传输请求。

#### 验收标准

- **WHEN** Quick Share 运行在当前用户的交互式 Windows 桌面会话中且处于后台或托盘状态，**THEN** 系统 **SHALL** 尽可能唤起对应窗口并请求用户注意。
- **WHEN** Windows 前台激活策略不允许强制抢占焦点，**THEN** 系统 **SHALL** 使用任务栏闪烁、通知或等价机制提示用户，不得静默丢弃请求。
- **WHEN** 已有模态选择窗口正在处理请求，**THEN** 新请求 **SHALL** 被明确标记为忙碌、排队或合并；不得叠加不可控的选择器窗口。
- **IF** Quick Share 运行在无交互桌面的服务会话、锁屏环境或无法显示 UI 的会话中，**THEN** 系统 **SHALL** 返回“需要本地交互/当前不可用”的明确状态，不得假装请求已接受。

### 2.8 取消、失败与状态反馈

**用户故事：** 作为任一端用户，我希望取消和异常都有明确结果，不产生误传或不完整文件。

#### 验收标准

- **WHEN** 任一选择窗口被取消，**THEN** 系统 **SHALL** 取消当前请求、通知远端、不启动新传输，并把取消作为正常终止而非应用错误。
- **IF** 远端离线、请求超时、选择内容在传输前失效、保存目录不可写或传输初始化失败，**THEN** 两端 **SHALL** 显示可区分的错误状态。
- **WHEN** 请求结束，无论成功、拒绝、取消或失败，**THEN** 系统 **SHALL** 关闭关联窗口并释放该请求占用的 UI 状态。
- **WHEN** 传输已经开始后用户取消，**THEN** 系统 **SHALL** 使用现有传输取消与临时文件清理机制，并向两端报告已取消。
- 日志可以记录请求 ID、稳定设备 ID、结果和诊断信息，但 **SHALL NOT** 记录完整敏感路径清单、设备密钥或传输令牌。

## 4. 技术约束

### 4.1 项目与平台约束

- Quick Share 2 是 Rust-only workspace；不得引入或恢复 Python 实现。
- 第一阶段的原生 GUI 实现目标仅为 Windows；Linux 原生选择器和 macOS 支持后续另行设计。
- Windows UI 必须运行在用户的交互式桌面会话中；不得依赖 Windows 服务会话直接显示桌面窗口。
- 应优先复用 `quick-share-platform` 的平台边界、`quick-share-protocol` 的消息模型，以及 `quick-share-transfer` 的身份、授权、清单、取消和接收安全能力。
- 具体 Windows UI 技术、线程模型和 crate 选型应在 design 阶段确定；不得为了显示选择器而引入绕过 Rust 安全约束的脚本式旁路。
- workspace 继续遵守 `unsafe_code = "forbid"`；若候选 Windows UI 方案要求项目内新增 `unsafe`，必须在设计评审中更换方案或单独作出明确决策，不得静默放宽 lint。

### 4.2 协议与状态约束

- 远程请求必须包含全局唯一请求 ID、请求方向、发起设备的已验证身份和必要的操作元数据。
- 协议至少需要表达：待确认、已接受、已拒绝、已取消、忙碌、不可交互、已过期和失败。
- 所有远程触发与响应必须经过现有认证和加密连接，不新增仅凭共享 URL、IP 或明文 HTTP 即可触发本地 UI 的入口。
- 请求必须具备有限有效期，并对重复请求保持幂等。
- 在用户确认源内容或目标目录之前，不得授予实际文件读写权限或启动数据流。
- 接收目标必须继续经过现有路径规范化、目录约束、临时文件和原子完成策略；GUI 选择结果不视为可以绕过安全校验的可信输入。

### 4.3 配置与隐私约束

- 每设备保存目录应写入 Quick Share 的平台配置目录，并采用可版本化、可安全迁移的格式。
- 目录记录必须以经过验证的稳定设备 ID 关联，不以显示名称或 IP 作为主键。
- 配置损坏时应安全回退为要求用户重新选择，不能导致应用无法启动或写入任意目录。
- UI 与日志不得泄露其他设备对应的保存目录；远端只需收到操作结果，不应收到 Windows 本地完整保存路径。

### 4.4 质量与兼容性约束

- 原生选择器、请求状态机、目录持久化和冲突策略必须可通过抽象接口进行自动化测试，核心行为不得只能依赖人工点击验证。
- 必须增加 Windows 目标的构建或编译检查，并保留非 Windows workspace 构建能力。
- 现有设备配对、身份变更检测、传输授权、路径安全、取消、恢复与错误清理行为不得回退。
- 文件夹递归发送应沿用现有符号链接和路径安全策略，不得通过选择文件夹引入目录逃逸。

## 5. 排除项

第一阶段明确不包含：

- Linux 原生图形文件、文件夹或保存目录选择器。
- macOS 原生选择器。
- Windows Shell 右键菜单、资源管理器扩展、拖拽投递等额外系统集成。
- 未经确认让未配对设备直接打开原生选择器或开始传输。
- 将单次未配对请求的接受自动视为永久配对。
- 仅依靠 IP 地址、主机名或设备显示名称建立信任。
- 在 Windows 服务 Session 0、无登录用户或无交互桌面的环境中强行显示 UI。
- 新建独立的明文远程触发通道，或绕过 Quick Share 现有加密、身份和授权链路。
- 自动同步、目录监控、定时传输、NAT 穿透或云端中继。
- 本需求未要求改变现有传输格式、断点续传算法或大文件分块策略；只有完成 GUI 工作流所必需的协议扩展属于范围内。
